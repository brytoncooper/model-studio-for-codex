# Codex projection consumer

Purpose: consume pending `registered_model.upserted` outbox events into consumer-owned projection files, and consume `registered_model.removed` events into conditional deletions of those files. This package is injected fake-materializer orchestration only; the `CodexProjectionMaterializer` is supplied by the caller and there is no real renderer, connection, or live integration.

Ownership: `CodexProjectionConsumer` owns exactly the four files in this package plus the owned test. It reads engine projection contracts (`ports`, `intents`, `receipts`, `file_port`) but never edits them. No other files, live state, or providers are touched.

Contracts: frozen `CONSUMER_ID`, `CodexProjectionWrite` (with `artifact_ref` derived as `path.as_posix()`), `CodexProjectionMaterializer.materialize`, marker `CodexProjectionMaterializationError` (message never persisted), `CodexProjectionDependencyError` for malformed file receipts, frozen `CodexProjectionItemResult` / `CodexProjectionBatchResult`. Constructor injects `ProjectionOutboxReader`, `ProjectionMutationIntentJournal`, `ConditionalProjectionFiles`, `ProjectionReceiptStore`, and the materializer. Entry point `consume_pending(limit=100)` returns an ordered batch.

Invariants: only `registered_model.upserted` and `registered_model.removed` are supported (anything else is skipped without touching dependencies); strict payload and mutation validation, with removal payloads carrying exactly `registration_id`, `removed: true`, and `revision` matching the event; `artifact_ref` validated with `receipts.validate_artifact_ref` plus absolute/traversal rejection before journal access; every file receipt validated (type, operation, path, expected hash, success reason/result/observed hash with observed matching the expected precondition, write noop valid only when expected equals the desired hash, delete noop valid only under an absent-only precondition, allowlisted conflict reasons per operation with postdelete interference excluded as write-malformed and postwrite interference excluded as delete-malformed) before any receipt-store call, and malformed receipts raise `CodexProjectionDependencyError` with no outcome recorded; for events requiring a mutation, `record_intent` precedes exactly one conditional file operation (`compare_and_write` for upserts, `compare_and_delete` for removals); exact current upsert receipt replays validate through the receipt store without a file operation; file `noop` is acknowledged as `applied`; file conflicts persist only `file_<allowlisted reason>`; no retries; unexpected dependency exceptions propagate with later events untouched.

Removal invariants: the deletion target and expected hash derive solely from prior applied artifact ownership for the same consumer and aggregate, never from the intent journal or matching bytes; every upsert reads current applied state before any file operation, including intent retries. Older revisions and equal revisions from another outbox row conflict as `stale_revision`. An exact current upsert receipt replay must match the artifact and rendered hash, validates through the receipt store, and never rewrites the file. Otherwise the write precondition derives from a replayed intent when one exists, or current applied state, with an `artifact_ref_changed` conflict on path moves. A removal with no prior applied state records the non-destructive `unresolved_no_prior_applied` conflict and fabricates no path, since artifact-less deletion has no contract support. An upsert strictly below the applied revision records `stale_revision` before any journal or file mutation, so a stale upsert never resurrects a newer tombstone; exact replay of the currently applied outbox row is exempt and equal revisions fall through to the receipt layer. An exact removal replay at the current applied outbox ID and revision requires a valid artifact reference and tombstone, revalidates the durable deletion receipt, and calls neither the file adapter nor journal. A hash-bearing receipt cannot replay as deletion. Other removals at or below the applied revision record `stale_revision` and never remove a newer file; content changes, foreign owners, and symlinks surface as `file_hash_mismatch`, `file_foreign_owner`, and `file_symlink` conflicts. Verified deletions record a tombstone via `record_deleted` with `output_sha256` null. An absent file on a first removal attempt is `file_missing`; only a retry carrying a proven prior ownership plus a matching recorded deletion intent for the same outbox row may acknowledge the absent file as deleted, and it unlinks nothing. A `missing` receipt must have both observed and result hashes absent; contradictory hashes raise `CodexProjectionDependencyError` without acknowledgment. A tombstone with a newer removal replays as an absent-only delete noop; a later upsert recreates from the absent-only precondition.

Extension: to support new event kinds or renderers, add explicit validation and tests here first. Crash retries stay conservative: a retry reuses the recorded intent and treats unexpected file state as a conflict rather than adopting it.

Tests: `cd python && PYTHONPATH=src python3.12 -m unittest tests.integrations.hosts.codex.test_projection_consumer` using call-logged fakes plus real SQLite producer/outbox/intent/receipt adapters and conditional files under temporary fixture roots. Integration tests cover stale intent retries after deletion, equal-revision tombstones, mutation-free exact acknowledgment replay, deletion crash recovery, foreign replacement protection, contradictory receipts, and later recreation. Fixture coverage includes deletion, crash-retry acknowledgment, foreign/symlink/content-changed conflicts, stale revisions, tombstone noop, and recreation after deletion.

Limitations: no real renderer, no connection support, and no live
integration. An intent-before-file retry can apply normally while the target is
still absent. A retry after first-create or replacement acknowledgment loss
reports the unexpected file state as a conservative conflict instead of
adopting it.

Revision guards compare the applied-state snapshot before the conditional file operation; they do not make SQLite and filesystem mutation one atomic cross-process transaction. Concurrent consumer scheduling still needs coordination by the caller.
